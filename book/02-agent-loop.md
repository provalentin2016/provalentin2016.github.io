# Глава 2. Цикл агента

В первой главе был конвейер: этапы идут один за другим, и каждый выдаёт артефакт. В этой главе речь о другом: о цикле, в котором модель сама решает, какое действие выполнить дальше, видит результат и продолжает. Это и есть агент в узком смысле слова.

Разница между конвейером и агентом принципиальна. В конвейере порядок шагов известен заранее. В агенте модель выбирает следующий шаг по ходу работы и должна уметь остановиться.

В истории Matterhorn этот переход занял примерно три месяца: с 17 апреля по конец июня 2024 года.

## 2.1. Минимальный цикл

Любой агент сводится к четырём вещам:

1. Модели передаётся состояние: задача, история, текущее содержимое проекта.
2. Модель возвращает действие в фиксированном формате.
3. Действие выполняется, и его результат (observation) добавляется в историю.
4. Цикл повторяется, пока модель не вызовет действие завершения или не кончится бюджет.

В коммите `SWE Agent initial commit` (17 апреля 2024) эта схема появилась в коде. Файлы, которые добавил коммит: `AgentActions.kt`, `IssueAgentWorker.kt`, `IssueSingleStepAgentWorker.kt`, `ResolveIssueAgentAction.kt`. Всего 338 добавленных строк.

Набор действий в первой версии был намеренно маленьким:

```kotlin
fun getAvailableActions(context: ExecutionContext): List<AgentAction> {
  return listOf(
    ShowProjectStructureAgentAction(),  // get_current_project_structure
    EditFileAgentAction(),              // edit_file
    CheckCompilationAgentAction(),      // проверка компиляции
    FinishAgentAction()                 // завершение
  )
}
```

Четыре действия — это весь мир агента. Всё остальное делается через них. Это правило работает и сегодня: чем меньше действий, тем проще модели выбрать правильное.

У каждого действия есть три части: имя, описание для модели и две функции — `review` (проверить запрос до выполнения) и `execute` (выполнить). Проверка до выполнения появилась сразу: модель могла запросить несуществующее действие или передать неверные аргументы, и это нужно было поймать до того, как что-то изменится на диске.

## 2.2. Observation: результат действия, который видит модель

Коммит `Add observation to the IssueActionPlanWorker` (17 апреля 2024) — маленький, три строки. Но он важен: без наблюдения модель не знает, что произошло. Она пишет `edit_file` и не видит, создался ли файл, компилируется ли он, нашлась ли строка для замены.

С этого момента в каждом шаге есть два сообщения: действие модели и наблюдение от среды. История растёт, и через несколько шагов контекст переполняется. Коммит — `reproduce swe-agent: add shortening of old user messages` (18 июня 2024) — ввёл сокращение: старые пользовательские сообщения (в том числе наблюдения) сворачиваются, а последние оставляются полными.

Позже это оформилось в `Last5ObservationsHistoryProcessor`. Его константа `MAX_FULL_USER_MSGS = 5`: пять последних пользовательских сообщений остаются полными, остальные сворачиваются, и модель получает короткое уведомление о том, сколько сообщений свёрнуто. Это ранний пример того, что позже стало компакцией истории (см. главу 14). Обратите внимание: лимит считается в сообщениях, а не в токенах. Это простое решение, и оно же его главный недостаток.

## 2.3. Формат ответа: где агент ломается чаще всего

Если бы нужно было выбрать одну причину, по которой агенты падают, я бы назвал формат ответа. Модель выдаёт текст, а код ожидает структуру. Несоответствие — и цикл останавливается.

В истории Matterhorn это проявилось очень явно. Ранний формат описывал действия свободным текстом:

```
Can't parse an action description:
```

Ошибка возникала, когда модель добавляла размышления, код-блоки или лишние разделители. Коммит от 15 мая 2024 переписал инструкцию. Ключевые изменения:

- Вместо свободного описания — явный блок `ACTIONS:` с разделителями `------`.
- Каждое действие описано тремя полями: `ACTION`, `ARGUMENTS`, `DESCRIPTION`.
- Явное правило: «If this is not an action, but just text/reasoning/code, then remove it from the answer».
- Пример правильного ответа прямо в промпте.

В сообщении коммита причина названа прямо: проблемы с GPT-4o. Модель менялась, и формат, который работал на одной версии, ломался на другой. Это общий урок: **формат ответа — часть контракта с моделью, и его надо тестировать при каждой смене модели**.

Вторая волна изменений формата пришла через SWE-agent. Коммит — `change action format (make similar to swe-agent), add demo` (17 июня 2024). Формат стал ближе к исходному SWE-agent: команда и аргументы в блоке bash. Позже, (29 августа 2024), парсер научили разбирать блоки ```` ```bash ````, потому что модели часто оборачивали команды именно в них.

## 2.4. Воспроизведение SWE-agent

Для Matterhorn идеей было не изобретать цикл заново, а взять известный подход. В июне 2024 года появилась серия коммитов с префиксом `reproduce swe-agent:`. Из них видно, что именно переносили:

- `add shellInterface, add all commands` (10 июня). Интерфейс к bash: агент выполняет команды в постоянной сессии.
- `add exit code control for single-line bash commands` (17 июня). Код возврата каждой команды возвращается агенту.
- `fixes for multiline commands` (14 июня). Многострочные команды выполняются отдельно от однострочных.
- `set 40 steps maximum (see figure 14, 15 from swe-agent paper)` (18 июня). Лимит шагов взят из статьи SWE-agent: на графиках видно, как качество растёт и где выходит на плато.

Лимит шагов — хороший пример того, как общий исследовательский результат становится константой в коде. Значение 40 не выведено из задачи Matterhorn, оно взято из статьи и проверено на собственных данных только частично (в истории нет метрик).

Примечание: в истории нет таблиц с результатами сравнения. Утверждать, что «40 шагов оптимально для Matterhorn», нельзя. Можно утверждать, что так решили.

## 2.5. Инструменты редактирования

Самая трудная часть агента — редактирование файлов. Модель может написать файл целиком, заменить фрагмент или вставить строки. Каждый способ имеет свои ошибки.

В августе 2024 года (`MTHRN-269`) появилась серия коммитов о способах редактирования:

- `add ReplaceLinesWorker` (20 августа 2024). Замена по номерам строк.
- `fix bug with wrong syntax error in SearchReplaceWorker` (19 августа 2024). Замена по фрагменту: модель должна точно воспроизвести исходный текст.
- `drop redundant response types, put edit workers into separate package` (22 августа 2024).
- `Refactoring of EditWorkers` (6 и 9 сентября 2024).

Редактирование по номерам строк быстро ломается, если модель ошиблась на единицу. Редактирование по фрагменту ломается, если модель поменяла пробелы. Итоговая схема: несколько специализированных воркеров (`SearchReplaceWorker`, `RewriteFileWorker`), каждый со своим форматом, и отдельный шаг, который проверяет результат.

Этот шаг — **RankingCritique**. Коммит от 10 августа 2024 добавил тип воркера `RankingCritique`. Он получает список предложенных действий (`actionsToRank`) и возвращает для каждого ранг и оценку. Формат ответа проверяется тем же механизмом `UserReviewedRequest`, что и в главе 4: если число рангов не совпадает с числом действий, модель получает сообщение об ошибке и отвечает снова. Стоит дороже одного вызова, но дешевле, чем откатывать неверную правку.

Коммит от 18 сентября 2024 добавил настройку `EditWorkerCritique` через переменную окружения. То есть критик был опциональным: его можно было включать и выключать без пересборки.

## 2.6. Что работает, а что нет

К концу июня 2024 года у агента было всё, что нужно для работы: цикл, наблюдения, история, набор действий, редактирование. Но он оставался хрупким, и основные усилия ушли не на новые возможности, а на устойчивость формата и инструментов.

Таблица того, что было важнее:

| Проблема | Решение в истории |
|---|---|
| Модель не выдаёт структуру | Явный формат с примером |
| Длинная история переполняет контекст | Пять последних сообщений полные, остальные свёрнуты |
| Правка ломает файл | Несколько воркеров редактирования и критика |
| Агент не видит результат | Наблюдение после каждого действия |
| Цикл не заканчивается | Лимит шагов |

## 2.7. Судьба в текущем коде

Цикл, наблюдения и действия пережили переходы: класс `IssueSingleStepAgentWorker`, созданный в коммите «SWE Agent initial commit», всё ещё есть в HEAD (в пяти файлах), а `ExecutionContext` и `ArtifactRequestExecutor` стали основой ядра. История сокращения сообщений тоже жива, но с переименованиями. В `ej-core/.../agent/history_processors/HistoryProcessors.kt` значение `Last5Observations` всё ещё есть в перечислении `HistoryProcessors`. Класс ответа переименован в `LastNObservationsResponse`, а сериализованное имя осталось `Last5ObservationsResponse`: по нему агент может восстановить историю из сохранённых данных, поэтому менять его без миграции нельзя.

Ушли конкретные решения, которые описаны здесь как историческая точка. `RankingCritique`, `IssueActionPlan` и формат с блоком `ACTIONS:` в HEAD не встречаются. Действия `edit_file`, `get_current_project_structure` и `check_compilation` тоже не найдены: набор инструментов агента в текущей версии другой. Если вы хотите воспроизвести формат из этой главы, опирайтесь на эту книгу и коммиты, а не на текущий код.

## Упражнение

1. Реализуйте минимальный цикл агента с четырьмя действиями из раздела 2.1 (чтение файла, запись файла, запуск команды, завершение). Используйте любую модель через API. Залогируйте каждое действие и наблюдение.
2. Сломайте формат ответа намеренно: попросите модель отвечать «в свободной форме» и посмотрите, как быстро падает парсер. Затем добавьте явный формат с примером и проверьте на той же задаче.
3. Ограничьте историю последними пятью наблюдениями и сравните, как меняется качество на задаче из 15 шагов.
