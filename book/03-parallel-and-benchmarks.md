# Глава 3. Параллельность и бенчмарки

[← Назад](02-agent-loop.md) · [Оглавление](README.md) · [Далее →](04-recipes-knowledge.md)

Агент, который работает в одном потоке и выполняет одну задачу, почти ничему не учит. Чтобы понять, насколько он хорош, нужно запустить его много раз на разных задачах. Чтобы делать это за разумное время, нужна параллельность. А параллельность в агенте одновременно и ускоряет работу, и ломает всё, что предполагает последовательный порядок: логи, интерфейс, общее состояние проекта.

Эта глава о том, как Matterhorn пришёл к параллельному запуску. Начиналось всё с бенчмарка, а не с продукта.

## 3.1. Первый бенчмарк: HumanEval

Самый ранний эксперимент, который виден в истории, — решение задач HumanEval. (В репозитории есть более ранние коммиты, например от 19 марта 2024 года, но они не про эксперименты.) Это стандартный набор задач на написание функций на Python по описанию и набору тестов. Для агента он удобен: задача короткая, результат проверяется автоматически, эталон известен.

Первый коммит — `Initial HumanEval solving` (22 марта 2024). Через неделю появились:

- `running tests until HumanEval problem is solved` (2 апреля 2024). Агент запускает тесты в цикле и правит код, пока тесты не пройдут. Это зародыш того, что позже стало проверкой в цикле агента.
- `Refactoring HumanEval workers` (10 апреля 2024).
- `Enable running HumanEval in command-line mode` (15 апреля 2024). Теперь эксперимент можно запускать без IDE. Это решающий шаг: без CLI нельзя запускать эксперименты в CI.
- `Run HumanEval problems in parallel` (16 апреля 2024).

Здесь важный момент для книги. В истории нет ни одного коммита с итоговой долей решённых задач. Нельзя сказать, сколько задач решал агент в апреле 2024 года и насколько версии отличались друг от друга. Результаты, если они существовали, лежали в логах CI или в таблицах, которых в репозитории нет. Поэтому в книге я не буду приводить цифры точности, а опишу только инфраструктуру.

## 3.2. Параллельная обработка задач

Как устроен параллельный запуск, видно из коммита от 16 апреля 2024. Раньше задачи шли циклом с обработкой ошибок:

```kotlin
for (problem in input.problems) {
  try {
    // генерация решения для одной задачи
  } catch (e: Exception) {
    // Ignore the problem
  }
}
```

Стало так: каждая задача — отдельная корутина, а ошибки считаются в счётчике:

```kotlin
var failedProblem = AtomicInteger(0)

coroutineScope {
  input.problems.map {
    val problem = it
    async {
      try {
        // генерация решения для одной задачи
      } catch (e: CancellationException) {
        throw e                       // отмену не глотаем
      } catch (e: Exception) {
        failedProblem.incrementAndGet()  // считаем, а не игнорируем
      }
    }
  }.awaitAll()
}
```

Три детали здесь важны, и каждая повторяется в других местах истории.

**Отмену нельзя глотать.** `CancellationException` перебрасывается наверх. Иначе кнопка «Stop» не сможет остановить параллельные задачи. Эта же ошибка всплывала в коммитах про отмену (глава 5).

**Ошибки считаются.** В исходном коде ошибка одной задачи молча пропадала. После изменения её можно увидеть в статистике. Для бенчмарка это принципиально: молчаливо проигранная задача выглядит как «не попыталась».

**Порядок не гарантирован.** `awaitAll` ждёт всех, но результаты приходят в произвольном порядке. Всё, что опирается на порядок (например, логи в файл), нужно переписывать.

## 3.3. Многопоточность в IDE

Проблемы начались, когда параллельные задачи стали писать в одно место: в чат IDE, в дерево артефактов, в общий объект состояния.

Коммит от 29 марта 2024 — один из самых показательных. Его сообщение: «Switch to request batch processing instead of streaming to avoid UI freezing. When several threads are writing their results to the chat, it leads to UI freezing». То есть потоковая выдача результата в чат с нескольких потоков вешала интерфейс. Решение: копить ответы и отправлять пакетами.

Урок простой и общий: **интерфейс — тоже общий ресурс, и параллельная запись в него требует такой же дисциплины, как запись в базу**. Пакетная отправка медленнее в теории, но быстрее на практике, потому что интерфейс не перерисовывается на каждом токене.

Следующий шаг — `Fix multithreading issues` (16 апреля 2024). В одном коммите переписаны `ExecutionContext` и `RootExecutionContext`: вместо ручного управления потоками появилась функция `parallelProcess`, которая запускает задачи через `async` и `awaitAll` и учитывает время выполнения. Коммит также убрал старые вызовы `EDT` и `readText`, которые создавали блокировки между потоками.

Ошибка «Access from Event Dispatch Thread (EDT) is not allowed» всплывала несколько раз. Коммит от 5 сентября 2024 — отдельная починка этой ошибки. Общее правило из истории: всё, что трогает UI или VFS, идёт через явный переход на нужный поток, а не через надежду, что вызов сработает.

## 3.4. Логи, которые нельзя перепутать

Параллельный запуск порождает логи, которые невозможно прочитать. Десять задач пишут «testStarted», «testFinished», «testFailed» в один вывод, и через минуту понятно только, что что-то упало.

Matterhorn использовал формат сервисных сообщений TeamCity. Это текстовые строки вида `testStarted name='...'`, которые CI умеет разбирать и показывать как дерево тестов. Для одного потока формат работает. Для параллельного запуска не работает: сообщения разных задач перемешиваются, и CI не понимает, какой тест чей.

Решение — идентификатор потока (flowId). Коммит от 16 апреля 2024 добавил его в каждое сообщение (сокращённый пример из формата):

```
testStarted name='solve_problem_12' flowId='...'
testFinished name='solve_problem_12' flowId='...' duration='4312'
```

Сообщения одного теста теперь связаны одним идентификатором, даже если между ними пришли сообщения других тестов. Дальше понадобилась экранировка: коммит от 5 июня 2024 применил к flowId те же правила, что к имени теста. Коммит от 4 июня 2024 заменил пробелы на подчёркивания в `TeamCityLogger`. Причина в сообщении коммита не указана; по смыслу это тот же класс проблемы: пробелы ломали разбор атрибутов.

Отдельно, в коммите от 20 мая 2024, — применение `toTeamCityFormat()` к именам тестов. Без этого любой символ, который TeamCity считает служебным, ломал разбор всего блока.

Вывод: **когда агентов много, каждое событие должно нести идентификатор того, кому оно принадлежит**. Этот принцип в более зрелом виде вернётся в главе 19, где события Junie Live привязаны к инстансам.

## 3.5. CI как лаборатория

TeamCity в истории проекта — не только инструмент для тестов. Он стал средой выполнения агента:

- `Use "." working directory on TeamCity` (15 июля 2024). Агент на CI должен работать в корне checkout, а не в каталоге IDE.
- `Always generate images using OpenAI on TeamCity` (28 августа 2024). Конфигурация CI отличается от локальной: на CI провайдер для картинок зафиксирован. Причина в сообщении не объяснена; по смыслу это ради воспроизводимости.
- `Temporarily replace recipe for TeamCity` (4 сентября 2024). Рецепт на CI подменили временно. Почему, в сообщении не сказано.
- `Report to teamcity if backend or frontend generation is failed` (29 августа 2024). Ошибка генерации теперь видна в CI как провал теста, а не просто как строка в логе.

Здесь проявилась интересная связка: CI одновременно проверяет агента (тесты кода, который он написал) и является его испытательным стендом (бенчмарк). Это два разных режима, и в истории они перемешаны.

## 3.6. Параллельные правки одного проекта

Самое сложное — когда несколько параллельных агентов меняют один и тот же проект. Коммит от 31 июля 2024, `Run tests in parallel and merge changes`, сделал так: каждая попытка работает с копией исходников (`source.copy()`), а её результат сливается обратно в основной проект. Если слияние не проходит, включается запасной путь: отдельный агентный шаг `Apply changes` получает текст несработавших правок и просит модель воспроизвести тот же результат заново. То есть слияние при неудаче решает ещё одна попытка агента, а не человек. Это удобно, но делает ошибку слияния дорогой: она стоит ещё одного вызова модели.

Позже появились `Refactoring of EditWorkers` (сентябрь 2024) и `EditWorker: Fixed issue with same artifactId for different critique attempts` (26 сентября 2024). Последний коммит показателен: два параллельных варианта правки получили один идентификатор артефакта, и один перезаписал другой. Такие ошибки невозможно поймать в одном потоке.

Рекомендация из истории: **идентификатор артефакта должен включать попытку, а не только объект, над которым работали**.

## 3.7. Что из этого следует

1. Бенчмарк нужен раньше продукта. Matterhorn начал с HumanEval, по-видимому потому, что без автоматической проверки нельзя понять, улучшилось ли что-то.
2. Параллельность требует трёх вещей: не глотать отмену, считать ошибки и связывать события с источником.
3. Интерфейс — такой же общий ресурс, как база данных, и с ним нужна та же дисциплина.
4. CI можно использовать как лабораторию, но тогда его конфигурация становится частью эксперимента.

## 3.8. Судьба в текущем коде

Инфраструктура надёжнее, чем конкретные задачи. `TeamCityLogger` и `ArtifactRequestExecutorService` остались в `core/src/main/kotlin/.../helpers/` и `.../ArtifactRequestExecutorService.kt`, то есть механизм сервисных сообщений TeamCity и исполнитель запросов к модели живы. Классы HumanEval-бенчмарка удалены: в HEAD их нет. Правило «отмену не глотать» сохранилось: в `core/` около шестнадцати мест ловят `CancellationException`, и в проверенных примерах (`AICaches.kt`, строка 185) исключение перебрасывается дальше. Это правило стоит проверять при каждом рефакторинге параллельного кода.

## Упражнение

1. Возьмите набор из 20 простых задач (например, HumanEval или свой). Напишите цикл, который решает их последовательно, и измерьте время. Затем переведите цикл на параллельный запуск через `async`/`awaitAll` с ограничением числа одновременных задач. Сравните время и количество ошибок.
2. Добавьте в лог каждой задачи идентификатор запуска. Проверьте, что при параллельной записи в один файл строки можно разделить по задачам.
3. Намеренно сломайте обработку отмены (проглотите `CancellationException`) и проверьте, что кнопка остановки перестала работать. Это лучший способ запомнить правило.
