# Глава 4. Рецепты: знания, которые агент не должен выдумывать

Модель знает много, но не всё, и тем более не знает, как сегодня правильно подключить Google OAuth к Express-приложению или какую версию библиотеки ставить. Если её не подсказать, она придумает. Иногда придумает хорошо, чаще — API, которого нет, или библиотеку, которую не стоит использовать.

Matterhorn решил это через **рецепты** (recipes): проверенные инструкции с примерами кода, которые агент может подключить к задаче. Рецепт — это не просто документация. Это структурированный объект, у которого есть описание, зависимости, фрагменты кода и правила применения.

Эта глава — одна из самых поучительных, но с оговоркой, которую нужно знать с самого начала: **в текущем HEAD репозитория каталога рецептов нет**. Он жил в подсистеме генератора, которую удалили в ноябре 2025 года. Об этом — в конце главы.

## 4.1. Проблема: модель не знает последних версий

В апреле 2024 года Matterhorn генерировал приложения, которые использовали внешние сервисы: Google Calendar, Google Sheets, OpenAI, Slack. Модель знала эти API по обучающим данным, но:

- не знала актуальной версии клиентской библиотеки;
- путала параметры OAuth;
- не знала, что в проекте уже есть нужная зависимость, а что нужно поставить.

Первый ответ был очевидным: положить в промпт документацию. Но документация длинная, а контекст дорог. Нужен был механизм, который подбирает только релевантные знания.

## 4.2. Каталог и индекс

Первый коммит — `Basic implementation of recipe catalog` (18 апреля 2024, задача MTHRN-75). Идея: рецепты лежат в ресурсах плагина, каждый описан в файле `*.recipe.yaml`, а модели передаётся только индекс: короткий список путей и описаний.

Схема в упрощённом виде:

```
Задача от пользователя
   └─ RecipeLookupWorker
        ├─ получает индекс: [{path, description}, ...]   ← коротко
        ├─ модель выбирает пути подходящих рецептов       ← JSON-массив
        ├─ проверка: путь есть в индексе?                 ← UserReviewedRequest
        └─ рецепты + их зависимости → в промпт генератора  ← полные инструкции
```

Воркер `RecipeLookupWorker` появился в коммите от 29 апреля 2024 (MTHRN-76). Ключевая деталь в коде: модель должна вернуть JSON-массив путей, и каждый путь проверяется по индексу:

```kotlin
return@UserReviewedRequest "Path '$path' doesn't have corresponding knowledge base entry"
```

Если модель выдумала путь, ответ отклоняется, и модель получает сообщение об ошибке и пробует снова. Это тот же механизм `UserReviewedRequest`, что и в главе 2 для формата действий. Проверка выполняется на стороне кода, а не доверяется модели.

Почему важен индекс, а не полный каталог: модель выбирает из короткого списка, а полный текст получает только выбранные рецепты. Экономия контекста и меньше шума.

## 4.3. Структура рецепта

Структура рецепта менялась несколько раз. Первая формальная версия описана в коммите от 30 апреля 2024 через документирующие комментарии в `RecipeContent.kt`:

```kotlin
@Serializable
open class RecipeContent(
  val topics: List<String> = emptyList(),   // 1–2 слова, категории
  val description: String,                  // попадает в индекс
  val depends_on: List<String> = emptyList(), // рецепты, которые нужно применить раньше
  val instructions: String                  // инструкции для модели
)
```

Здесь три разных назначения. `description` — только для выбора рецепта. `instructions` — только для применения. `depends_on` — для порядка. Разделение важно: если описание пишется для модели, которая что-то выбирает, оно отличается от инструкции для модели, которая пишет код.

Позже структура стала богаче. Файл рецепта Google OAuth в версии уже выглядит так:

```yaml
topics:
  - "google authentication"
description: |-
  How to access Google APIs for OAuth authentication.
scopes:
  - Backend
dependencies:
  - "googleapis@135.0.0"
snippets:
  - source: src/GoogleAuthService.ts
    target: src/services/GoogleAuthService.ts
  - source: src/GoogleAuthController.ts
    target: src/controllers/GoogleAuthController.ts
instructions: |-
  # Initialize GoogleAuthService.
  ...
```

Новые поля появились по мере необходимости:

- `scopes` (22 мая 2024, MTHRN-101). Рецепт задаёт, для бэкенда он или для фронтенда (`RecipeScope`: `Frontend`, `Backend`). Судя по названию задачи, нужен был способ не применять рецепт не к той части проекта.
- `snippets` (коммит от 7 мая 2024, MTHRN-80). Вместо того чтобы описывать код словами, рецепт может содержать готовый файл. Судя по коду (`snippet.source` → `snippet.target`), это способ передать готовый библиотечный код без пересказа.
- `protected` (коммит от 7 июня 2024, «Add an option to mark recipe snippets as protected»). Фрагменты с такой пометкой отмечены как защищённые. Точное поведение в сообщении коммита не описано; его стоит смотреть в коде.
- `dependencies` с закреплённой версией. (7 мая 2024): «Set version of googleapis library in the recipe». Версия фиксируется в рецепте, а не выбирается моделью.

## 4.4. Зависимости: что агент может установить

Агент, который может выполнять `npm install`, может установить что угодно. Это опасно и по безопасности, и по стабильности. Matterhorn ограничивал это в два шага.

**Первый шаг: белый список.** Коммит от 18 апреля 2024, `whitelist installed npm dependencies`. Логика в `NpmRunWorker`: если список одобренных зависимостей не задан, пакет ставится последней версией без проверки. Если задан, а пакета в нём нет, операция отклоняется. Список лежит в проекте в `.llm/dependencies.json`, и сообщение об отказе прямо на него ссылается:

```
<пакет> is not in the list of approved dependencies.
See `.llm/dependencies.json` for the list of approved dependencies.
```

**Второй шаг: проверка перед установкой.** Коммит от 7 мая 2024 (MTHRN-96), `Check that requested dependencies exist`, добавил `AddNpmDependencyProjectAction`. В его методе `review` есть `npm add --dry-run`: команда пробует установку без записи на диск. Если пакет не существует или версия не найдена, модель получает ошибку до того, как что-то изменилось.

Заметьте порядок: сначала проверка в белом списке, потом dry-run, и только потом реальная установка. Каждый шаг дешевле предыдущего, а отказ на любом шаге не оставляет следов.

Коммит MTHRN-79 от 6 мая 2024 добавил автоматическую установку зависимостей рецепта («Install required npm dependencies automatically»). Теперь установка идёт из рецепта, а не из решения модели.

## 4.5. Ошибка, которую откатили

Самый поучительный эпизод — `MTHRN-99 Embed recipe for config into template and guidelines` (14 мая 2024). Идея: встроить рецепт конфигурации прямо в шаблон и в инструкции, чтобы модель не вспоминала, как читать `.env`. Через три недели её откатили: `Revert "...MTHRN-99..."` (4 июня 2024), и параллельно `Rollback config from templates and return to the good old process.env` (4 июня 2024).

Причина в сообщениях коммитов не записана. По порядку событий видно, что решение было не в том, чтобы объяснять конфигурацию лучше, а в том, чтобы вернуться к простому механизму, который модель не может перепутать: переменной окружения (`process.env`). Тем же днём откатили и `MTHRN-110 Hardcode backend port in the template` (добавлен 17 мая, откатан 4 июня): порт бэкенда тоже был зашит в шаблон.

Урок для книги: **рецепт полезен для знаний, которые модель может применить по-разному, и вреден для вещей, которые должны быть однозначными**. Конфигурацию лучше задавать кодом, а не текстом.

## 4.6. Правила, которые появились из ошибок

Рецепты пополнялись по мере того, как агент ошибался. Самый понятный пример — рецепт SQLite. Он появился в коммите от 17 июля 2024, а потом получил серию правок:

- `Add a line about unsupported operator to SQLite recipe` (26 июля 2024);
- `Add examples to rules in SQLite recipe` (29 июля 2024);
- `Add a rule about managing write operations to SQLite recipe` (12 августа 2024).

Каждая правка — правило, которое появилось после конкретной ошибки. Это ручной аналог того, что сегодня называют «evals»: ошибка фиксируется, и правило закрепляется в знаниях. Рецепт становится историей его провалов.

Та же логика видна в рецепте для OpenAI: `Add a rule about model usage to the openai recipe` (6 августа 2024). Сообщение коммита не описывает конкретную ошибку, поэтому связь с ней — предположение; сам факт правила записан.

## 4.7. Рецепты для фронтенда и сборка проекта

В августе 2024 года рецепты разделились по фронтенду: `Add recipes for frontend (antd and bootstrap)` (20 августа 2024), затем `shadcn` (2 сентября 2024) и `animations` (3 сентября 2024). Выбор UI-библиотеки стал отдельным решением, которое принимает рецепт, а не модель. Коммит от 20 августа 2024 уточняет: если библиотека не задана, по умолчанию используется antd.

Два коммита показывают, как рецепты встраивались в поток:

- `Let SWE know about guidelines and recipes` (28 августа 2024). Агент с циклом из главы 2 теперь видит рецепты.
- `Add paths to all recipes to prompt` (30 августа 2024). Пути рецептов попали в промпт, и агент мог обратиться к ним по имени.

## 4.8. Граница: что рецепт не решает

Рецепт не заменяет проверку. Даже правильный рецепт модель может применить неправильно. Поэтому рядом с рецептами в истории всегда были проверки: компиляция, тесты, dry-run, белый список (глава 3 и глава 5).

В коде есть ещё одно ограничение, которое стоит знать. Функция `RecipeCatalog.lookup` рекурсивно обходит `depends_on`:

```kotlin
fun lookup(recipePath: String): List<Recipe> {
  val recipe = recipes[recipePath] ?: return emptyList()
  return recipe.content.depends_on.flatMap { lookup(it) } + recipe
}
```

В версии из коммита проверки на циклы нет: если рецепт A зависит от B, а B от A, рекурсия не остановится. Я проверил именно эту версию. На практике каталог, видимо, не содержал циклов, но гарантии в коде нет. Для собственной реализации это ошибка, которую стоит предотвратить сразу: `visited`-множество решает задачу в три строки.

## 4.9. Судьба рецептов

Здесь нужно быть точным, потому что это меняет смысл всей главы.

- Каталог рецептов жил в `webgen-main/src/main/resources/recipes/` и в связанных пакетах `webgen/recipes/`.
- Последний коммит, связанный с рецептами, от 13 октября 2025, `[declarative-generator] Support env variables for recipes`.
- Коммит от 28 ноября 2025, `Remove Kineto`, удалил 1577 файлов и 151 412 строк. В списке удалённого — 264 файла с «recipe» в пути, включая `webgen/recipes/RecipeCatalog.kt`, `RecipeContent.kt`, `workers/RecipeLookupWorker.kt`, `workers/RecipeApplyWorker.kt` и ресурсы `recipes/shadcn`, `recipes/custom-ui-components`.
- В HEAD нет ни одного файла `*.recipe.yaml`, а `RecipeCatalog` отсутствует.

Что дожило до текущего кода: механизм `UserReviewedRequest` (`core/src/main/kotlin/.../requests/UserReviewedRequest.kt`), который проверяет формат ответа модели. Его использует и агент из главы 2, и поиск по индексу из этой главы в первоначальной версии. Идея «модель выбирает из индекса, код проверяет выбор» пережила конкретную реализацию.

Итог для книги: глава описывает реальный и работавший механизм, который был удалён вместе с генератором. Это не провал, но читатель должен знать, что актуальный Junie построен иначе, и не искать рецепты в текущем коде.

## Упражнение

1. Создайте каталог из 5–10 рецептов в формате YAML: `description`, `depends_on`, `instructions`. Реализуйте поиск: модель получает только индекс `description`, возвращает JSON-массив путей, код проверяет каждый путь по индексу и отклоняет выдуманные.
2. Добавьте в рецепт зависимость, которая образует цикл (A → B → A). Проверьте, что ваш `lookup` зависает или падает. Затем добавьте `visited`.
3. Найдите задачу, на которой модель ошибается стабильно. Напишите одно правило в рецепт, запустите ту же задачу и сравните результат. Это минимальная версия цикла «ошибка → правило».
