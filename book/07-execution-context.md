# Глава 7. Контекст выполнения: кто что держит и когда отпускает

В главе 2 агент превратился в цикл, в главе 5 мы говорили об отмене и бюджете. Но у цикла есть вопрос, который в демонстрационном коде обычно не задают: **кто владеет ресурсами, которые открыты во время работы?** Процесс bash, HTTP-соединение, сессия MCP-сервера, файл журнала, подписка на события. Если агент завершил задачу, а процесс остался жив, пользователь увидит «зомби» в системе. Если закрыли ресурс, который ещё использует другой шаг, получим ошибку в случайном месте.

В Matterhorn эту задачу решает пара классов: `RootExecutionContext` и `ExecutionContext`. Эта глава разбирает, как они устроены и почему их правила записаны так подробно.

## 7.1. Два уровня: корень и узел

Контекст выполнения — это дерево. Корень (`RootExecutionContext`) существует один на задачу или сессию. Узлы (`ExecutionContext`) создаются на каждый запрос к артефакту и образуют дерево вызовов.

Конструктор узла показывает связь:

```kotlin
class ExecutionContext(
  val root: RootExecutionContext,
  val parent: ExecutionContext?,
  val request: ArtifactRequest<*, *>,
  val data: ExecutionContextData?,
) : CustomArtifactEventLogger
```

У каждого узла есть `root`, `parent` и запрос, который он выполняет. Потомки создаются через `createChildContext`. Статистика (время, токены, стоимость) считается на уровне узла, а агрегируется по дереву. В текущем виде классы впервые появляются в импорте кода 11 июля 2024 года; в дальнейшем их основные понятия менялись мало.

Разделение нужно потому, что у корня и узла разная продолжительность жизни. Корень живёт, пока жива задача, и отвечает за ресурсы. Узел живёт один запрос и отвечает за учёт: сколько времени и денег потрачено на этот шаг. Смешать их значит либо закрывать ресурсы при каждом шаге, либо копить учёт бесконечно.

Чтобы контекст доходил до всех корутин, которые запускает агент, используется элемент корутинного контекста:

```kotlin
class ExecutionContextElement(val uuid: UUID) : AbstractCoroutineContextElement(ExecutionContextKey)
```

Элемент нужен, чтобы контекст доходил до корутин, которые агент запускает, в том числе параллельных задач из главы 3.

## 7.2. Два способа зарегистрировать ресурс

Корень хранит «пользовательские данные» (`userData`) — ресурсы и сервисы, привязанные к ключам. Регистрация бывает двух видов, и разница между ними — главное правило всего механизма:

- `registerContext(key, value)` **одалживает** значение. Корень только ищет его по ключу. Если значение реализует `AutoCloseable`, это не делает его собственностью корня. Закрывать его будет кто-то другой.
- `registerOwnedContext(key, value)` **передаёт владение**. Корень закроет значение при завершении. Значение обязано реализовывать `CustomContext` и `AutoCloseable`.

Правила из документа `docs/root-execution-context-lifecycle.md` звучат жёстко: владение переходит только при успешной регистрации; закрывать владеемый ресурс самостоятельно нельзя; передавать его другому корню тоже нельзя. Заменить владеемый экземпляр через любой ключ нельзя: это бросает `IllegalStateException`.

Зачем два вида? Пример из кода: сервис, который один на весь плагин (клиент LLM, кэш), должен быть одолжен задачам. Процесс bash, открытый для конкретной задачи, должен закрываться вместе с ней. Если бы всё было «владеемым», общий сервис закрывался бы при первой же задаче. Если бы всё было «одолженным», процессы утекали бы.

Тесты класса `RootExecutionContextCloseTest` записывают эти правила как спецификацию. Их восемнадцать, и названия читаются как требования: `close leaves borrowed closable contexts open across roots`, `borrowed registration cannot downgrade ownership`, `neither registration API can replace an owned instance`. Для собственного агента я бы начинал именно с таких тестов: они фиксируют поведение раньше, чем появляется сложная логика.

## 7.3. Закрытие: один раз, в порядке регистрации

Метод `close()` устроен аккуратно:

```kotlin
fun close() {
  val contexts = synchronized(userData) {
    if (closed) return
    closed = true
    ownedContexts.toList()
  }
  var cancellation: CancellationException? = null
  for (context in contexts) {
    try {
      context.close()
    } catch (e: CancellationException) {
      if (cancellation == null) cancellation = e
      else if (cancellation !== e) cancellation.addSuppressed(e)
    } catch (e: Exception) {
      logger.warn("Failed to close context ${context::class.java.simpleName}", e)
    }
  }
  listener.onContextClosed(this)
  cancellation?.let { throw it }
}
```

Здесь четыре решения, каждое из которых стоит запомнить.

**Закрытие под блокировкой только один раз.** Флаг `closed` выставляется внутри `synchronized`. Повторный вызов возвращается сразу. Даже если первое закрытие ещё идёт, второй вызов не ждёт его и не запускает очистку повторно.

**Ресурсы закрываются по одному, в порядке первой регистрации владения.** Порядок важен: если позже зарегистрированный ресурс зависит от раньше зарегистрированного, он должен закрыться первым. Порядок здесь не обратный (как в стеке), а в порядке регистрации: первый зарегистрированный закрывается первым. Документ этого не объясняет, и для вашего агента порядок стоит выбирать явно и записывать.

**Обычное исключение логируется, очистка продолжается.** Один сбойный ресурс не должен мешать остальным.

**Отмена перебрасывается в конце.** Первое `CancellationException` сохраняется, остальные добавляются как подавленные. Очистка и уведомление слушателя при этом выполняются полностью, и только потом исключение уходит наверх. Это то же правило, что в главе 5: отмена — не ошибка, но её нельзя проглотить.

Ошибка JVM (`Error`) обрабатывается иначе: она прерывает очистку сразу, и повторной попытки нет. Тест `JVM errors escape cleanup and are not retried` фиксирует это. Логика простая: `OutOfMemoryError` или `StackOverflowError` означают, что состояние процесса ненадёжно, и продолжать очистку опасно.

## 7.4. Гонки регистрации и закрытия

Самое тонкое место — регистрация, которая происходит одновременно с закрытием. Документ описывает три гарантии:

- регистрация после начала закрытия бросает `IllegalStateException`;
- регистрация, которая гонится с закрытием, либо успевает и попадает в очистку, либо не успевает и остаётся у вызывающего кода;
- поиск ресурса после закрытия работает, но возвращённый ресурс может уже быть закрыт.

Последнее правило неочевидно. Поиск не блокируется, и вызывающий код получает ссылку, которая может стать недействительной в любую миллисекунду. Поэтому ресурсы, которыми пользуются асинхронно, должны проверять состояние сами. Тест `registration racing with close either transfers ownership or rejects it` проверяет именно первую гарантию: никакого третьего исхода, когда ресурс потерян, быть не должно.

Заметьте, что очистка выполняется вне блокировки регистрации. Тест `concurrent close returns while cleanup runs outside the registration monitor` проверяет, что второй вызов `close()` возвращается, пока первый ещё закрывает ресурсы. Если бы очистка шла под блокировкой, любой ресурс, который при закрытии пытался бы что-то зарегистрировать, создавал бы взаимную блокировку.

## 7.5. Отдельный сценарий: наблюдатель плана

В сентябре 2026 года коммит `JUNIE-5206 (PR B of 3): release PlanContext and coroutine children on task/root close` добавил документ, который описывает самостоятельный сценарий standalone-агента. Он стоит отдельно, потому что показывает, как корень и дочерние корутины завершаются вместе.

Корень standalone-агента владеет `PlanContext` и одалживает общие сервисы проекта. Класс `StandaloneAgentRunner` закрывает корень в `finally`, то есть при любом исходе. `PlanContext.close()` запрашивает отмену наблюдателя, но не ждёт очистки и не отменяет ни родителя, ни соседей. В обратную сторону: отмена родителя останавливает наблюдателя.

Документ описывает асимметрию как намеренную. Наблюдатель плана — вспомогательный процесс, и если он не остановился мгновенно, это не должно задерживать завершение задачи. Но если задача отменена, наблюдатель обязан остановиться тоже.

## 7.6. Что изменилось с 2024 года

Цепочка изменений показывает, как менялось понимание контекста:

- **11 июля 2024** — код импортирован, корень и узел существуют с самого начала.
- **17 сентября 2024** — контекст агента хранится в `ExecutionContext` как `userData`. Появился ключ `ExecutionContextUserDataKey`: агент больше не передаёт состояние через параметры, а ищет его в дереве.
- **28 октября 2024** — коммит «close context to avoid leak» закрывает контексты, которые раньше утекали. Утечки здесь — прямое следствие того, что владение не было явным.
- **29 августа 2025** — коммит «Refactor to minimize usages of ExecutionContext (replace with Runtime)». Вместо одного общего контекста появились узкие интерфейсы, наследующие `CustomContext`: `StopHookRuntime`, `PermissionRequestHookRuntime`, `ExternalHookRuntime` и другие. Каждый видит только то, что ему нужно.
- **23 сентября 2026** — владение `PlanContext` и дочерними корутинами стало явным, и появились документ и тесты.

Важно: переход на узкие интерфейсы не отменил `ExecutionContext`. В `ej-core/src/main` его по-прежнему используют в 212 файлах. Узкие `Runtime`-интерфейсы — это срез, а не замена. Так часто бывает при рефакторинге больших систем: новая абстракция наслаивается, а старая остаётся, пока её не удалят по частям.

## 7.7. Что из этого следует

1. **Владение нужно записывать явно.** Если ресурс может быть одолжен или передан, это должно быть видно в API, а не в комментариях.
2. **Закрытие должно быть идемпотентным и безопасным при гонках.** Повторный вызов возвращается сразу, а регистрация после закрытия падает.
3. **Отмена и ошибка при очистке — разные вещи.** Очистка выполняется полностью, отмена возвращается в конце.
4. **Фиксируйте правила тестами.** Названия тестов в `RootExecutionContextCloseTest` работают как спецификация лучше, чем документ.
5. **Дерево — хорошая модель для учёта.** Статистика по узлам суммируется наверх, а ресурсы живут на уровне корня.

## Упражнение

1. Реализуйте корень с двумя видами регистрации (одолженный и владеемый ресурс). Напишите тесты: регистрация после закрытия падает, повторное закрытие ничего не делает, владеемый ресурс закрывается ровно один раз.
2. Добавьте ресурс, чьё `close()` бросает обычное исключение, и проверьте, что остальные ресурсы всё равно закрываются и слушатель уведомляется.
3. Добавьте ресурс, который бросает `CancellationException`. Проверьте, что исключение появляется наверху только после очистки всех остальных ресурсов.
4. Запустите параллельно регистрацию и закрытие сотни раз. Убедитесь, что ни один ресурс не теряется: каждый либо закрыт корнем, либо остался у вызывающего кода.
