# Глава 10. Тестировать недетерминированного агента

Обычный тест проверяет, что функция для одного входа даёт один выход. С агентом это не работает. Одна и та же задача может дать разные решения, разные последовательности действий и разные формулировки. Каждый прогон стоит денег и занимает минуты. Тестировать «на глаз» невозможно, а запускать полный прогон на каждое изменение дорого.

Matterhorn решил задачу многоуровнево. Ниже пять уровней, от дешёвого к дорогому, и самое интересное в них — кэш запросов к модели, который превращает недетерминированные вызовы в воспроизводимые. Эта глава описывает их по порядку.

## 10.1. Уровни проверки

Пирамида выглядит примерно так:

| Уровень | Что проверяет | Стоимость | Где запускается |
|---|---|---|---|
| Модульные тесты | логику без модели | почти нулевая | каждый коммит |
| Тесты с записанным ответом модели | поведение агента на известных ответах | низкая | каждый коммит |
| Проверка кэша в CI | неизменность исходящих запросов к модели | низкая | каждый PR |
| E2E тесты собранного бинарника | интерфейс и запуск CLI | средняя | сборки |
| Evals (оценка на задачах) | качество решений | высокая | по запросу |

Нижние уровни ловят регрессии дёшево, верхние — качество дорого. Важно не путать их роли: зелёный модульный тест не говорит, что агент стал лучше, а проваленный eval не всегда означает, что сломан код.

## 10.2. Кэш запросов: записать один раз, воспроизводить всегда

Главная идея: сохранить ответ модели на каждый запрос и при повторном запросе отдавать сохранённый ответ. Тогда прогон становится детерминированным. Модель вызывается только при первом запуске или при изменении запроса.

Кэш реализован в `core/llm/.../AICaches.kt` с двумя вариантами: локальный (`LocalAICaches`, файлы в каталоге Junie) и Redis (`RedisAICaches`, общий для CI). Первая версия Redis-кэша появилась 27 августа 2024 года.

Ключ кэша — хеш **нормализованного** запроса. Нормализация описана в `AICacheKey.kt`:

```kotlin
internal fun String.fixUnstableTextForCaches(): String {
  // времена выполнения, идентификаторы трассировки, временные пути сборки,
  // адреса объектов в памяти, хеши версий — всё, что меняется между запусками
  ...
}

fun fromText(text: String): AICacheKey {
  val fixed = text.fixUnstableTextForCaches()
  return AICacheKey(initialKey = text, stableKey = fixed, stableKeyHash = fixed.hash256())
}
```

Здесь два ключа. `initialKey` — исходный текст запроса, нужен для отладки: по нему можно понять, что именно отправлено. `stableKey` — текст после удаления нестабильных частей, его хеш и есть ключ. Сохранение обоих делает кэш понятным: при промахе видно, какой запрос не нашёлся.

Нормализация — самое опасное место всей схемы. Если она слишком слабая, в ключ попадают случайные детали, и кэш промахивается на каждом запуске. Если она слишком сильная, она скрывает реальные изменения, и кэш отдаёт старый ответ на новый запрос. Баланс зашит в список регулярных выражений. Тест `scratch normalization leaves unrelated paths unchanged` проверяет, что нормализация не трогает посторонние пути: она может случайно затереть полезные части.

Почему запрос, а не вход задачи? Потому что ответ модели зависит от всего, что ушло в запрос: промпта, описания инструментов, истории беседы. Любое изменение в этих частях меняет ключ. Это свойство, а не недостаток: кэш сам показывает, что запрос изменился.

## 10.3. Запись промахов

Кэш полезен, только если видно, когда он промахнулся. Для этого промахи записываются в два файла, которые появились в октябре 2024 года вместе с рефакторингом «введение одного места для сохранения и загрузки кэша»:

- `NonCachedRequests` — хеш каждого запроса, которого не было в кэше;
- `LLMRequestsFull` — полный стабильный текст такого запроса.

Первый файл даёт список промахов, второй — то, что именно изменилось. Без второго разбираться с промахом приходится вручную.

## 10.4. Redis: кто первый записал

В Redis запись идёт командой `setnx` — «записать, если ключа ещё нет»:

```kotlin
val keyWasSet = commands.setnx(key.stableKeyHash, json.encodeToString(response))
if (!keyWasSet && canReadFromRedis)
  commands.get(key.stableKeyHash)?.let { return json.decodeFromString<AIAnswer>(it).asCached() }
```

Если два параллельных агента одновременно запросили одно и то же, первый записывает ответ, а второй видит, что ключ уже есть, и читает записанный ответ. Оба получают один результат. Без `setnx` второй затёр бы первый, и при долгом воспроизведении ответы бы расходились.

Флаги `MATTERHORN_CAN_READ_FROM_REDIS` и `MATTERHORN_CAN_WRITE_TO_REDIS` отделяют чтение от записи. Это важно для CI: сборка может читать общий кэш, но не должна его менять. Записывать в общий кэш может только тот, кто отвечает за него.

## 10.5. CI: изменение запросов — это изменение поведения

В README репозитория написано, что слияние запрещено, если провалилась одна из проверок: «Check Redis Cache», «Check Agent Execution», «Check Redis Cache (Standalone)» или «Build & Check». Проверка «Check Redis Cache (Standalone)» делает нечто особенное: она **проигрывает** набор эталонных задач по записанным ответам и проверяет, что исходящие запросы к модели не изменились.

Если запрос изменился, сборка падает с сообщением `Failure (Redis cache misses)`. В артефактах лежат `cache_misses.json` и `detailed_cache_misses.json`. Правило из навыка по расследованию сборок такое:

1. Посмотреть первый промах в каждом экземпляре: остальные обычно являются следствием первого.
2. Если изменение не должно было затрагивать запросы, исправить код, чтобы запрос снова совпал.
3. Если изменение запланировано, объяснить его инженеру, который отвечает за модель, и он обновит кэш. Самостоятельно обновлять общий кэш нельзя.

Здесь скрыта важная идея. **Промпт, описание инструмента и порядок истории — это контракт с моделью, и его изменение должно быть видно в ревью.** Обычно изменение промпта выглядит как правка текста и проходит незамеченной. Кэш делает его событием, которое требует объяснения. Цена — каждая правка промпта требует дополнительного шага.

Заметьте, что проверка не говорит, стал ли агент лучше. Она говорит только, что запросы не изменились. Качество проверяется другими уровнями.

## 10.6. E2E: собранный бинарник как пользователь

Кэш проверяет логику, но не то, как программа запускается. Для этого есть модуль `cli-e2e-tests`. Он запускает собранный бинарник Junie CLI внутри Docker через псевдотерминал (PTY) и описывает взаимодействие через **экраны**: тест видит то, что видит пользователь, и отправляет ввод так же, как пользователь.

Модуль появился в марте 2026 года и работает в трёх режимах. E2E-тесты в Docker проверяют установленные сборки (Release, EAP, Nightly). Snapshotter-тесты запускаются локально, без Docker, и пишут читаемые логи снимков экрана — для быстрой итерации. Snapshotter-сервер открывает тот же терминал по HTTP: внешний агент может отправить ввод (`POST /input`), получить снимок (`GET /snapshot`) и остановить сессию. Последний режим — пример того, что инструменты для тестирования агентов тоже становятся агентами.

## 10.7. Evals: оценка качества на задачах

Качество решений проверяют evals. Модуль `ej-app/cli-evals` появился в октябре 2025 года. Он запускает CLI как внешний процесс и собирает результат. Его код показывает, какие проблемы решает оценка:

- **Жёсткий лимит времени.** Комментарий в `CliAgentExecutor` говорит, что при превышении лимита «the process tree is killed». Убивается всё дерево процессов, а не только родитель. Агент, который запустил сборку, оставит её работать, если убить только главный процесс.
- **Построчные логи с метками времени.** Класс `TimestampedLine` хранит исходную строку и время её захвата отдельными полями. Комментарий объясняет причину: не менять исходную строку, например, не вставлять метку времени в JSON. Иначе последующий разбор ломается.
- **Инкрементальная запись.** Каждая строка вывода передаётся обработчику сразу, чтобы логи сохранились даже при аварийном завершении.

Evals дорогие. Для навыка, который запускает внешние CI-тесты агента, в документе прямо сказано: прогон регрессии занимает от 20 до 50 минут и стоит около шести долларов, а прогон по цели — около одного доллара. Такие тесты запускаются только по явному запросу. Это хороший пример того, что стоимость тестирования нужно учитывать так же, как стоимость самого агента.

## 10.8. Хронология: от кэша к оценкам

Вот как развивалась тестовая инфраструктура:

- **27 августа 2024** — кэш запросов в Redis. Первая версия, которая позволила проверять агента без повторных вызовов модели.
- **14 октября 2024** — единое место для сохранения и загрузки кэша, с записью промахов.
- **24 октября 2025** — `cli-evals`, оценки CLI как внешнего процесса.
- **3 февраля 2026** — инструкции по CI добавлены в README, включая список обязательных проверок.
- **11 февраля 2026** — ключ кэша строится от финального текста запроса (коммит «Apply AI Caches for the final text of AI Request»).
- **18 марта 2026** — E2E-модуль и Snapshotter.

Порядок показательный: сначала научились не тратить деньги на повторы (кэш), потом — ловить изменения запросов (CI), потом — проверять интерфейс (E2E) и качество (evals).

## 10.9. Что из этого следует

1. **Воспроизводимость — это кэш.** Записанный ответ модели превращает недетерминированный вызов в детерминированный тест.
2. **Ключ кэша — это граница между «то же самое» и «другое».** Нормализация должна быть явной и покрытой тестами.
3. **Промпт — контракт.** Его изменение должно быть видно в ревью и объясняться.
4. **Логируйте промахи.** Без полного текста запроса промах бесполезен для диагностики.
5. **Общий кэш пишет один владелец.** Остальные только читают.
6. **Внешний процесс нужно ограничивать жёстко.** Лимит времени и убийство дерева процессов обязательны.
7. **Стоимость тестов — часть проектирования.** Дорогие проверки запускаются по запросу, дешёвые — всегда.

## Упражнение

1. Реализуйте кэш: ключ — хеш запроса, значение — ответ модели. Сохраняйте и `initialKey`, и нормализованный `stableKey`. Проверьте, что два запроса, отличающиеся только временной меткой, дают один ключ.
2. Напишите нормализацию, которая удаляет временные пути сборки. Добавьте тест: путь с нормальным именем не меняется, путь с временным каталогом сворачивается.
3. Добавьте проверку «исходящие запросы не изменились»: проиграйте три эталонных задачи по записанному кэшу и упадите, если появился промах. Затем намеренно измените промпт и убедитесь, что проверка падает и показывает первый промах.
4. Напишите оценку: запустите CLI-агента как процесс с лимитом времени 60 секунд. При превышении убейте всё дерево процессов. Проверьте, что дочерний процесс, запущенный агентом, тоже остановлен.
