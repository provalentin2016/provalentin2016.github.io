# Глава 12. Из IDE в терминал: standalone и CLI

Первые полтора года агент жил внутри IDE: с марта 2024 по июль 2025 года. Он видел открытые файлы, индекс проекта, панель инструментов и единственного пользователя, который сидит перед экраном. Чтобы агент стал продуктом, который можно запустить в терминале, в CI, в редакторе через протокол или в Slack, пришлось отделить его от IDE. Эта глава о том, как это сделали, какие части переехали, какие остались, и почему самая сложная часть оказалась не в агенте, а в запуске.

## 12.1. Что значит «standalone»

Standalone — это не просто «CLI без окна». Это отдельное приложение, у которого нет хозяина в виде IDE: оно само читает конфигурацию, само хранит сессии, само показывает интерфейс и само обновляется. Модуль `ej-app/cli-standalone` вырос из первого коммита «Junie standalone project scaffolding» (16 июля 2025 года). В HEAD в нём около 3800 файлов.

Структура пакетов показывает, как распределились обязанности. Самые большие группы:

| Пакет | Файлов | За что отвечает |
|---|---|---|
| `tui` | 585 | терминальный интерфейс: экраны, ввод, слэш-команды |
| `acp` | 385 | протокол для редакторов (Agent Client Protocol), глава 17 |
| `framework` | 71 | общий каркас приложения |
| `utils` | 62 | вспомогательные утилиты |
| `ide` | 39 | мост к IDE, когда она есть |
| `extensions` | 38 | расширения |
| `sandbox` | 30 | песочница, глава 15 |
| `gateway` | 28 | шлюз для многопользовательских сценариев, глава 19 |
| `migration` | 22 | перенос данных между версиями |
| `session` | 20 | сессии: сохранение и продолжение |
| `trust` | 17 | доверие к проекту |
| `allowlist` | 14 | разрешённые действия, глава 8 |
| `updates` | 13 | обновление и перезапуск приложения |

Видно, что интерфейс и протокол занимают большую часть модуля. Агент — это ядро в `core` и `ej-core` (глава 6). Standalone — обвязка вокруг него: без ядра не работает, но ядро без обвязки не продукт.

## 12.2. Один бинарник, несколько режимов

Точка входа — `Main.kt` с функцией `main(vararg args)`. Она решает, в каком режиме работать. Режимов несколько:

- **интерактивный** — TUI, по умолчанию;
- **ACP** — флаг `--acp` для интеграций с редакторами; появился в октябре 2025 года, одновременно с первой ACP-поддержкой;
- **headless** — неинтерактивный запуск одной задачи для скриптов и CI;
- **gateway** — отдельный процесс-шлюз, который принимает клиентов по сети (он собирается отдельным модулем `cli-gateway`).

Один бинарник с режимами выбран сознательно: один набор зависимостей, одна версия, одна конфигурация. Цена — стартовое время и размер. Документация по параметрам показывает, как режимы выбираются флагами и переменными окружения (`JUNIE_ACP` эквивалентен `--acp`).

Из `Main.kt` видно и ещё одну деталь: переменные окружения и аргументы логируются при запуске. Функция `startupLogEntries` пишет их в журнал, а отдельные флаги `--dump-env-vars` и `--dump-cmd-parameters` выводят их для диагностики. Это полезно, когда пользователь пишет «не работает» и никто не знает, какие настройки реально применились.

## 12.3. Каталог на диске

Отдельное приложение должно хранить своё состояние где-то, кроме проекта. С октября 2025 года это `JUNIE_HOME` (глава 11). Туда попадают логи, настройки, версии, сессии и кэш. Документ `junie-cli-user-disk-storage.md` перечисляет подкаталоги, в том числе `teleport/`. Команда `/teleport` появилась 3 ноября 2026 года: она упаковывает разговор, контрольные точки и незакоммиченный код в git bundle, но без значений переменных окружения. Так сессию можно продолжить на другой машине и не утечь секреты.

Здесь интересен выбор того, что **не** пакуется. Переменные окружения содержат ключи, и переносить их нельзя. Незакоммиченный код переносится, потому что без него работа не продолжается. Граница проведена явно и записана в документации, а не оставлена на усмотрение пользователя.

## 12.4. Перезапуск и обновление

Агент, который работает часами, рано или поздно нуждается в обновлении. Перезапуск процесса — неочевидная операция: надо сохранить сессию, отпустить терминал и запустить новую версию так, чтобы она подхватила состояние. Механизм `ProcessRestart` появился 8 октября 2026 года («Feat Restart Command»). Он работает через файл, путь к которому передаётся в переменной `JUNIE_RESTART_FILE`. Старый процесс атомарно записывает в файл идентификатор сессии и путь к проекту (сначала во временный файл, затем переименованием). Новый процесс читает файл при запуске. Перезапуск требует запуска через управляемый лаунчер: без него код явно сообщает об ошибке.

Схема с файлом — типичный компромисс для кроссплатформенного приложения. Перезапуск через exec работает не везде, особенно на Windows. Файл проще, но его нужно валидировать: устаревший или повреждённый файл не должен запускать неверную сессию. Атомарная запись нужна, чтобы новый процесс никогда не прочитал наполовину записанный файл.

## 12.5. Нативный лаунчер: почему не хватило Java

Самая неожиданная часть standalone — лаунчер. Junie распространяется как пакет, внутри которого есть JVM и приложение. Пакет создаёт jpackage, и он же создаёт стандартный запускающий файл. Этот файл делает три вещи: находит JVM, передаёт ей параметры и запускает приложение. Проблема в том, что у такого лаунчера нет понятного поведения в двух местах: процесс получает другое имя (в списке процессов виден не `junie`), а переменные окружения вроде `JDK_JAVA_OPTIONS` влияют на запуск неожиданным образом.

Поэтому в ноябре 2026 года в репозитории появился `native-launcher/` — небольшая программа на Rust. Её README описывает контракт прямо. Лаунчер загружает `libjli.dylib` из встроенной JVM и запускает JVM **в своём же процессе** через `JLI_Launch`. Процесс остаётся тем же: то же имя, тот же PID, тот же код возврата, та же реакция на сигналы.

Детали контракта показывают, сколько мелочей нужно учесть:

- лаунчер находит свой реальный путь через `realpath`, чтобы работать через символические ссылки;
- параметры JVM читаются из файла `jvm.options`, а не из встроенного списка;
- к параметрам всегда добавляются обязательные (`--enable-native-access=ALL-UNNAMED`, путь к приложению), и они стоят **после** пользовательских, чтобы их нельзя было переопределить;
- на macOS `JLI_Launch` возвращается в `main` из нового потока Java, и лаунчер должен это распознать.

Почему Rust, а не Kotlin/Native? В `AGENTS.md` написано, что Kotlin/Native добавляет сборщик мусора и потоки и не поддерживает все нужные платформы (например, Windows arm64). Решение сознательно выбрано против единообразия стека. Язык лаунчера — не предпочтение, а следствие ограничений платформ.

Урок для собственного агента: **если поставляете приложение с JVM или другой средой, сам запускающий файл — часть продукта**. Его поведение с именем процесса, сигналами и переменными окружения пользователи замечают раньше, чем баги в агенте.

## 12.6. Что из этого следует

1. **Standalone — обвязка вокруг ядра.** Ядро агента не меняется от того, что приложение теперь в терминале. Меняются интерфейс, хранение и запуск.
2. **Один бинарник с режимами** проще в поддержке, чем несколько продуктов, но стартует медленнее.
3. **Состояние — отдельный каталог**, и граница между тем, что переносится, и тем, что нет, должна быть явной.
4. **Перезапуск через файл** проще exec, но файл нужно записывать атомарно и валидировать.
5. **Лаунчер — часть продукта.** Его контракт с ОС надо описать и проверять.
6. **Диагностика в запуске.** Лог параметров и дамп окружения окупаются при первом же обращении в поддержку.

## Упражнение

1. Соберите простой CLI-агент с двумя режимами: интерактивным и headless (одна задача из аргумента). Общее ядро должно быть одним модулем. Проверьте, что ядро не зависит от способа ввода.
2. Реализуйте перенос сессии: упакуйте историю диалога и незакоммиченные изменения в один файл, не включая переменные окружения. Проверьте, что сессия восстанавливается на чистой копии проекта.
3. Реализуйте перезапуск через файл, путь к которому передаётся переменной окружения. Запись делайте через временный файл и переименование. Проверьте три случая: файл валиден, файл отсутствует, файл повреждён. Во всех трёх новый процесс должен запуститься, и только в первом он восстанавливает сессию.
4. Запустите приложение через стандартный лаунчер и через свой минимальный (можно на любом языке, который создаёт процесс с нужным именем). Сравните имя процесса и реакцию на `Ctrl+C`.
