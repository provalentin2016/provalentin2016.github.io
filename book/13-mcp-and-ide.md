# Глава 13. Инструменты снаружи: MCP и IDE как поставщик инструментов

Агент умеет читать файлы, править их и запускать команды. Но реальной задаче нужны и другие возможности: база данных, GitHub, браузер, документация, сборка, отладчик IDE. Писать под каждую из них собственный инструмент в ядре агента — тупик: ядро раздувается, а каждая интеграция требует новой версии продукта.

Протокол MCP (Model Context Protocol) решает это иначе: внешний сервер сам объявляет свои инструменты, а агент подключается к нему как клиент. В этой главе две стороны этой идеи. Первая: Junie как MCP-клиент, который подключает внешние серверы. Вторая: IDE как MCP-поставщик, который отдаёт агенту свои возможности. У каждой стороны свои трудности, и обе хорошо видны в истории.

## 13.1. Junie как клиент MCP

Клиент живёт в модуле `core/mcp`. Его классы показывают, из чего состоит интеграция: `McpClient`, `McpClientService`, `McpTool`, `DiscoveredMcpTool`, `McpServerConfiguration`, а для авторизации — `OAuthAuthService`, `OAuthAuthorization`, `McpOAuthDiscovery`.

Сервер подключается двумя способами, и это закреплено в типе `McpServerType`:

- **Local** — процесс на машине пользователя, общение через стандартный ввод и вывод;
- **Remote** — размещённый сервер по HTTP или HTTPS.

Первый коммит интеграции — «Added mcp server integration» от 20 мая 2025 года. Конфигурация серверов хранится в файле `mcp.json` в каталоге `.junie/mcp` проекта или в домашнем каталоге пользователя. Схема этого файла менялась: изменение от 23 июня 2025 года («Changed mcp settings schema») показывает, что конфигурация сразу стала предметом миграций, и это правильно: формат файла — внешний контракт (глава 11).

Отдельная деталь — аргументы процесса. Коммит «Preserve mcp arguments with quoting» (14 августа 2025) исправил потерю кавычек при запуске локального сервера. Судя по названию, речь о том, что аргумент с пробелом при передаче через оболочку мог распасться на части. Такие ошибки невидимы на тестовом сервере и ломают жизнь пользователю с путями, в которых есть пробелы. Урок: аргументы процесса надо передавать списком, а не строкой, которую кто-то потом разбирает.

## 13.2. Проблема: слишком много инструментов

Главная трудность MCP — не протокол, а бюджет. Каждый сервер приносит свои инструменты, а каждый инструмент — это описание, которое уходит в каждый запрос к модели. Десять серверов по десять инструментов — сто описаний в контексте. Модель тратит на них деньги и внимание, и выбирает инструмент хуже, когда вариантов много.

Решение в Junie — фильтр возможностей. Агент, который отвечает за выбор, видит список установленных серверов и задачу и решает, какие серверы нужны именно сейчас. Класс `CapabilityFilterExecutor` появляется в истории 11 февраля 2026 года. Его результат (`CapabilityFilterResult`) определяет, какие инструменты попадут в контекст агента.

Здесь важна асимметрия: фильтр может ошибиться. Если нужного сервера не оказалось в выборке, агент не сможет им воспользоваться, даже если он установлен. Поэтому для этого случая есть инструмент `enable_mcp`, появившийся 6 февраля 2026 года.

Его описание в коде говорит о правилах прямо:

> Enable an MCP server that was filtered out by the capability filtering agent. Use this tool when you need tools from an MCP server that is installed but currently unavailable.

Инструмент работает только для серверов, которые установлены и были отфильтрованы. Если сервер не установлен, инструмент честно отвечает «is not installed». Если сервер и так доступен, — «should already be available». Каждый отказ объясняет причину. Это важное свойство: инструмент, который молча ничего не делает, потом стоит часов отладки.

Модель получает два уровня доступа: обычный выбор фильтром и явное включение по запросу. Так экономится контекст, и при этом агент не заперт в неверной выборке.

## 13.3. Авторизация: OAuth в агенте

Сервера с удалённым доступом требуют авторизации. Поддержка OAuth появилась в декабре 2025 года («Refactored mcp oauth flow implementation», 6 декабря), а уже 12 декабря код OAuth перенесли в другой модуль (по сообщению коммита, в `ej-core-id`). Перенос через неделю после рефакторинга, судя по всему, означает, что первое размещение кода оказалось неудачным: авторизация относится скорее к инфраструктуре приложения, чем к ядру MCP-клиента.

Осторожность нужна в одном месте. Коммит «narrow MCP OAuth client_secret_post fallback» (октябрь 2026) сузил запасной путь авторизации: вместо любой возможной схемы — только `client_secret_post`. Расширение списка разрешённых способов авторизации удобно, но каждое новое разрешение — потенциальная дыра. Сужение здесь — правильное движение.

## 13.4. Результаты инструментов: размер имеет значение

Инструмент MCP может вернуть гигабайт текста. Если положить его в контекст как есть, модель потеряет всё остальное. Поэтому у действий MCP есть порог: `MCP_SUMMARIZATION_THRESHOLD`. Длинный результат сворачивается до сводки. Константа появилась в истории в марте 2026 года вместе с поддержкой структурированного вывода.

Это тот же приём, что для встроенных инструментов в главе 8 (порог 10 000 символов). Разница в том, что MCP-серверы сторонние: их выводы непредсказуемы. Порог — это защита от чужого кода, которая ещё и экономит деньги.

## 13.5. IDE как поставщик инструментов

Вторая сторона: IDE отдаёт агенту то, что знает только она. Сборка, отладчик, структура проекта, символы, статус VCS — всё это в IDE и почти нигде больше. Модуль `ide-server` — RPC-слой, через который Junie обращается к IDE.

Интересен способ, которым он сделан. Сервисы описываются не вручную, а схемой на собственном DSL. Файл `ide-server/README.md` показывает, что новый сервис начинается с файла схемы, в котором описаны записи и их поля:

```kotlin
val DoSomethingRequest = record("DoSomethingRequest") {
  string("input")
  int("limit", default = "10")
  bool("verbose", default = "false")
}
```

По схеме генерируются клиент и сервер. В репозитории это видно по именам файлов: `JunieBuildService`, `JunieBuildServiceClient`, `JunieBuildServiceServer`, а также `JunieChroniclesService` и `JunieAndroidService`. Для сервиса сборки есть все три файла, и они согласованы, потому что генерируются из одного описания.

Генерация защищает от типичного рассогласования: клиент и сервер расходятся в поле или в значении по умолчанию, и ошибка проявляется только при вызове. Цена — сложность генератора и необходимость помнить, что правится в схеме, а не в сгенерированном коде.

С января 2026 года IDE отдаёт агенту инструменты через MCP. Коммит «created ide-core architecture and introduce MCP toolsets in ide-server» (9 января 2026) ввёл эту архитектуру. Идея та же, что у внешних серверов: инструменты описаны протоколом, а агент их не знает заранее. Разница в том, что сервер — это сама IDE, и её инструменты зависят от открытого проекта.

Это даёт агенту доступ к возможностям, которых нет у внешнего сервера: например, к отладчику самой IDE. Но это же создаёт зависимость от IDE: без неё инструменты не работают. Отсюда связь с главой 6, где граница ядра и IDE-модулей была предметом решения.

## 13.6. Что изменилось в 2026 году

Сводка по хронологии:

- **20 мая 2025** — MCP-интеграция в клиенте.
- **23 июня 2025** — схема `mcp.json` меняется; конфигурация становится контрактом.
- **14 августа 2025** — исправлены кавычки в аргументах процесса.
- **6 декабря 2025** — OAuth для MCP.
- **9 января 2026** — MCP-инструменты IDE в `ide-server`.
- **6 февраля 2026** — `enable_mcp` для серверов, отфильтрованных фильтром возможностей.
- **11 февраля 2026** — фильтр возможностей появляется в истории в виде `CapabilityFilterExecutor`.
- **2 марта 2026** — сворачивание длинных результатов MCP.
- **Октябрь 2026** — сужение способов авторизации.

Видно, что 2025 год ушёл на подключение, а 2026 — на управление: сколько инструментов видит агент, кто решает, что включить, и что делать с большими ответами.

## 13.7. Что из этого следует

1. **Инструменты вынесите из ядра.** Протокол MCP позволяет добавлять возможности без новой версии агента.
2. **Бюджет инструментов — тоже бюджет.** Каждое описание стоит контекста, поэтому выборка нужна.
3. **Фильтр может ошибиться.** Нужен явный способ добавить инструмент по запросу, и отказы должны объяснять причину.
4. **Аргументы процесса передавайте списком**, а не строкой.
5. **Авторизацию держите отдельно** от клиента протокола и расширяйте список способов осторожно.
6. **Большие ответы сворачивайте** независимо от того, чей это инструмент.
7. **Схема — источник правды для RPC.** Клиент и сервер генерируются из одного описания.

## Упражнение

1. Подключите два MCP-сервера (можно простых, написанных самостоятельно): один с тремя инструментами, другой с десятью. Посчитайте, сколько описаний уходит в каждый запрос к модели.
2. Реализуйте фильтр: по задаче выбирайте один из серверов. Проверьте случай, когда нужный сервер не попал в выборку, и добавьте инструмент `enable_mcp`, который его включает. Отказ для неустановленного сервера должен объяснять причину.
3. Передайте аргумент с пробелом в локальный сервер: сначала строкой, затем списком. Убедитесь, что во втором случае аргумент приходит целым.
4. Напишите RPC-сервис по схеме: опишите запись с полями и значениями по умолчанию и сгенерируйте по ней клиент и сервер. Проверьте, что изменение значения по умолчанию в схеме попадает и в клиент, и в сервер.
