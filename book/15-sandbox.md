# Глава 15. Песочница: ограничить агента, не парализуя его

Агент, который выполняет команды в терминале, может сделать с машиной всё, что может пользователь. Он может удалить файлы за пределами проекта, прочитать ключи из `~/.ssh`, выкачать чужой скрипт и выполнить его. Обычно это предотвращают подтверждениями (глава 8): агент спрашивает разрешения на каждую команду. Но подтверждения быстро становятся шумом: если пользователь нажимает «да» сто раз за задачу, он перестаёт читать. Нужен другой слой: песочница, которая ограничивает то, что команда может сделать, независимо от того, что одобрил пользователь.

Эта глава описывает, как устроена песочница в Junie, что она защищает, где её границы и почему её поставка оказалась сложнее, чем сама идея.

## 15.1. Идея: ограничение на уровне процесса

Песочница оборачивает каждую команду агента во внешний инструмент `srt` (sandbox-runtime). Команда запускается с ограничениями: какие каталоги можно писать, какие читать, какие сетевые сокеты открывать. Ограничения действуют на уровне операционной системы, поэтому их нельзя обойти, просто переписав команду.

Здесь важно различие с подтверждениями. Подтверждение отвечает на вопрос «можно ли это сделать». Песочница отвечает на вопрос «что это может сделать, даже если разрешили». Два слоя дополняют друг друга: подтверждение для неочевидных решений, песочница для того, что нельзя разрешать по умолчанию.

Режим включается флагом `--sandbox` или командой `/sandbox`. Первая версия появилась 16 сентября 2026 года («Add opt-in terminal sandboxing to Junie CLI»). Слово «opt-in» в заголовке принципиально: песочница выключена, пока пользователь её не включил.

## 15.2. Политика по умолчанию

Что именно разрешено, задаёт файл политики. Значения по умолчанию видны в коде `SandboxPolicyDefaults`. Запись разрешена в проект (`${PROJECT_DIR}`), во временные каталоги (`${TMPDIR}`, `/tmp`) и в кэши инструментов: `~/.cache`, `~/.gradle`, `~/.m2`, `~/.npm`, `~/.cargo/registry`, `~/.rustup` и другие. Список длинный, и это намеренно: без кэшей сборка каждый раз скачивает зависимости заново, и агент становится бесполезным.

Чтение устроено иначе. Каталог `~/.ssh` запрещён целиком, но три файла из него разрешены явно: `config`, `known_hosts`, `known_hosts2`. Причина прагматичная: агенту нужно знать, на какие хосты ходить, но не читать приватные ключи. Граница проведена по назначению файлов, а не по каталогам.

Заметьте, как устроены правила: по умолчанию запрещено всё, что не записано в разрешённые списки. Обратное правило («разрешено всё, кроме…») быстро превращается в дыру, потому что новые опасные места появляются постоянно.

## 15.3. Файл политики нельзя редактировать молча

Самая тонкая часть — защита самой политики. Если агент может изменить файл, который определяет его ограничения, песочница бессмысленна: он просто разрешит себе всё.

Поэтому в `SandboxActiveContext` есть отдельный механизм. Правило записано в функции `authorizeEdits`:

```kotlin
if (paths.any { SandboxPolicyEditGuard.isPolicyTarget(policyFile, it) }) {
  val isSoleDirectTarget = paths.all { SandboxPolicyEditGuard.isDirectTarget(policyFile, it) }
  return if (isSoleDirectTarget && sandbox?.policyEditor != null) EditAuthorization.Allowed
  else EditAuthorization.Denied(...)
}
```

Редактирование файла политики разрешено только при трёх условиях: путь точно совпадает с файлом политики, это единственная цель правки в запросе и правка прошла явное подтверждение. Проверка учитывает символические ссылки: `isDirectTarget` отказывает, если цель — симлинк, и `isPolicyTarget` сравнивает файлы через `isSameFile`, а не только по строке пути. Иначе обход был бы возможен: ссылка с другим именем указывала бы на тот же файл политики.

Этот случай показателен. Защита должна учитывать не только то, что агент сказал, но и то, как файловая система интерпретирует путь. Строковое сравнение путей — самая частая дыра в такой проверке.

## 15.4. Что означает «литеральные аргументы»

Команды в терминале — это строки, и оболочка их интерпретирует. Аргумент `$(rm -rf ~)` внутри строки станет командой, если его не экранировать. Поэтому для песочницы введён структурированный режим. Его контракт записан в `docs/sandbox-srt-bundling.md` очень честно:

> The pinned runtime still executes shell strings on macOS and Linux. The guarantee is literal arguments through the adapter, not shell-free execution.

То есть гарантия — **аргументы передаются буквально**: каждый аргумент кодируется полным POSIX-экранированием в одинарных кавычках, апострофы и подстановки остаются данными. Но сама команда по-прежнему выполняется оболочкой. Документ прямо говорит, что выполнение без оболочки не обеспечено.

Честность в формулировке важна. Песочница без оболочки была бы сильнее, но её не было. Документ фиксирует, что именно гарантировано, и что ещё нет. Читатель, который поймёт «выполнение без оболочки», будет удивлён.

Здесь же видно разделение, которое мы встречали в главе 8: структурированные команды (аргументы списком) против строковых. Строковые команды нужны для намеренных shell-программ, например для диффа. Их не убирают, но помечают отдельно.

## 15.5. Поставка: почему не хватило системного srt

Идея песочницы проста. Поставка — нет. Инструмент `srt` — npm-пакет на Node. Если пользователь установит его сам, появляется зависимость от Node, а приложение, запущенное из Finder, часто не видит `node` в `PATH`. Поэтому Junie поставляет собственную сборку `srt` внутри пакета.

Решение: `bun build --compile` собирает из форка одиночный бинарник. Документ указывает конкретные цифры: arm64-бинарник весит 60,7 МБ, и проверка «запись вне `allowWrite` запрещена» прошла. Бинарник собирается в отдельном репозитории и публикуется как релиз. Потом пакет macOS и Linux его проверяет и подписывает.

Цепочка из нескольких шагов (сборка, публикация релиза, проверка, упаковка и подпись пакета) — по сути, отдельный проект. Документ описывает её на десяти разделах: от структуры контракта до устранения неполадок. Для агента это типичная картина: самая трудная часть — не логика ограничений, а то, чтобы бинарник оказался на правильной машине и с правильной версией.

Версии тоже закреплены: macOS сохраняет `0.0.71-jb.1`, Linux и локальные загрузки — `0.0.71-jb.2`. Закрепление нужно, потому что новая версия `srt` может изменить поведение ограничений, и проверки на старой версии перестанут что-то значить.

## 15.6. Статус: что включено и где

Документ фиксирует статус прямо: **EAP**. Песочница включена в EAP, nightly, experimental и dev-сборках для macOS и Linux. Для GA её не поставляют, а на Windows флаги `--sandbox` и `/sandbox` скрыты, и режим остаётся выключенным.

Это правильное решение. Песочница — дорогая в поддержке и новая, и её ошибки невидимы: команда просто падает с непонятным сообщением. Поэтому её выпускают постепенно, по каналам, и собирают сообщения о нарушениях. Для этого в коде есть `SandboxViolationMonitor` и хранилище отчётов о нарушениях (`SandboxViolationStore`).

Отдельная поддержка Linux появилась 25 сентября 2026 года («Support Linux sandboxing through the existing SRT integration»). Документ отдельно перечисляет системные требования Linux и политику для Unix-сокетов. Это типичный признак: одно и то же ограничение на разных ОС требует разных системных условий.

## 15.7. Чего песочница не делает

Честный список границ важнее списка возможностей:

- **Не делает выполнение без оболочки.** См. раздел 15.4.
- **Не работает на нативном Windows.** Адаптер не предоставляет ни sandbox, ни WSL-бэкенд.
- **Не проверяется на всех средах.** Документ прямо пишет: Linux и нативный Windows не проверялись в той же валидации, что macOS.
- **Не заменяет подтверждения.** Команда, разрешённая политикой, всё равно может быть вредной внутри разрешённых каталогов: например, стереть собственный проект. Для этого нужны подтверждения и версии правок (глава 8).

Последний пункт важен для собственного агента. Песочница защищает от выхода за пределы, но не от ошибки внутри них. Проект, который агент удалил целиком, остаётся внутри `${PROJECT_DIR}`, и песочница его не спасёт.

## 15.8. Что из этого следует

1. **Песочница — дополнительный слой поверх подтверждений**, а не замена им.
2. **По умолчанию запрещайте всё, что не записано в список разрешённых.**
3. **Защищайте файл политики** от редактирования агентом, учитывая символические ссылки и `isSameFile`.
4. **Документируйте гарантию точно.** «Литеральные аргументы» и «выполнение без оболочки» — разные утверждения.
5. **Закрепляйте версию инструмента**, от которого зависит ограничение.
6. **Выпускайте по каналам.** EAP, потом GA, и только после сбора данных о нарушениях.
7. **Честно пишите границы**: какие ОС проверены, что не покрыто.

## Упражнение

1. Реализуйте проверку пути с разрешёнными каталогами для записи. Проверьте четыре случая: путь внутри проекта, путь в `/tmp`, путь в `~/.ssh` и путь, который ведёт в проект через символическую ссылку из `/tmp`. Последний должен быть разрешён только если ссылка указывает внутрь проекта.
2. Напишите защиту файла политики: правка разрешена только при точном совпадении пути и без симлинка. Проверьте, что создание ссылки с другим именем и правка через неё отклоняются.
3. Передайте в команду аргумент `$(echo hi)` сначала строкой, затем через экранирование одинарными кавычками. Убедитесь, что во втором случае подстановка остаётся текстом.
4. Составьте список «что песочница не защищает» для своего агента. Для каждого пункта укажите, какой слой (подтверждение, версии, резервные копии) его закрывает.
